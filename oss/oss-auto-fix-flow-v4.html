Automated repair of minor OSS vulnerabilities

From a merge to main to a merged fix. Sonatype IQ Server, confirmed with SecOps, finds the vulnerability and recommends the version. Jenkins controls the flow. A Pi agent, with an LLM, maps the jar to the code and writes the tests. A person reviews the evidence only.

01Summary for the business caseText for the Proposal Summary box›

Problem statement

Minor OSS fixes follow the same manual path as major upgrades. The Nexus report goes to Dev. Dev applies the fix, tests it, and raises one pull request for each active release branch. The code has no tests around the jars, so each fix needs a manual check. A minor fix waits for a developer.

Solution

  1. Scope: Maven components and security policy violations only. Licence violations and non-Maven ecosystems stay on the manual path. v4
  2. Keep the current manual flow for major version upgrades of jars that the code calls.
  3. For a minor upgrade, a Jenkins job reads the Sonatype IQ Server result and the remediation version from the IQ API. Sonatype IQ Server with Lifecycle and Developer is in place. Golden versions are available. The agent applies the IQ-recommended version; it does not choose versions. v4
  4. A Pi agent maps the jar to the classes that call it, writes characterization tests for those classes, runs the tests on the current jar, applies the upgrade, and runs the tests again.
  5. The agent opens one pull request on Gitea with the pom change, the new tests, and both test reports. Jenkins backports the pull request to the active release branches. A vulnerable jar inside a shared internal library is fixed in the library first, then the consumers bump the library. v4
  6. Every finding without an active IQ waiver gets a fix. The Jocata Vulnerability Score orders the fixes. The pull request states for each jar if the code calls it. After the merge, the job writes the pull request link back to the violation in IQ.

Outcome

  • Minor OSS fixes follow one path: Jenkins, Sonatype IQ, Pi agent, pull request. No manual test step.
  • Code coverage grows. Each fix adds tests to code that has none.
  • Unused dependencies are removed. This reduces the attack surface and the scan noise.
  • Client audits see the full remediation list with a score and the evidence for each item, inside IQ Server, the tool SecOps already uses.

What, if not

Minor fixes stay manual. Dev keeps remediating, testing, and raising one pull request per release branch. Closure time stays tied to developer bandwidth. Code coverage does not grow.

03Scope and boundaries v4Maven only, security only, InnerSource, parent pom, artifact check, fan-out, rollback, bot account›

In scope

  • Maven components. Golden versions and the automated path exist for Maven. npm, containers, and other ecosystems that IQ scans stay on the manual path.
  • Security policy violations. IQ also raises licence violations. A version bump does not fix a licence problem. Licence violations go to Dev.
  • Minor upgrades of jars the code calls. Any upgrade, or a removal, of jars the code does not call. Section 09 has the matrix.

Shared internal libraries, InnerSource

The vulnerable jar often sits inside your own library. The consumer scan flags the jar, but the consumer does not declare it. IQ marks your own libraries as InnerSource components and attributes the finding to the library. The rule: fix the library first. The consumer bumps the library after the release.

Decision for the PoC

Does the library release run through the pipeline, or does a person cut it? If a person, the "blocked on upstream" state has a human step, and the P1 SLA depends on that person.

Version in a property or a parent pom

The version is often a property such as <jackson.version>, or sits in dependencyManagement of a parent pom. A change there touches every module that inherits it. Rules:

  • The maven-jar-usage skill runs per module. The pull request lists each module touched.
  • The after run is the full reactor build with all module tests, not one module.
  • If the parent pom is in another repository, a corporate parent, the fix is a release of that parent, then a parent version bump in each consumer. Same two-hop rule as InnerSource.

Artifact availability

The recommended version must be downloadable through Nexus Repository. If it is not present, or Repository Firewall quarantines it, the job logs an error with the GAV and the repository, marks the finding "blocked on artifact", and does not run tests. The repository admin unblocks it. The finding returns to the queue on the next scan.

Fan-out

One CVE in a shared jar opens a pull request in every repository on the same day. Reviewer capacity and the token budget hit at once. The repair job has a per-day cap on new pull requests. The queue order is by score, so P1 goes first across all repositories.

Rollback

A merged minor bump can still cause a production issue. The path is a revert pull request raised by Dev. The finding then goes to Dev with the revert link. The agent does not retry that component until Dev clears it.

Bot account

The agent commits as a bot account on Gitea. It can push to oss-auto-fix/* branches only. Branch protection on main stays. Its token lives in Jenkins credentials, scoped to the repair job.

Dependabot

  • Security data from GitHub advisories. Not used here.
  • Does not read an IQ report. Does not write tests.
  • GitHub only. The code is on Gitea.
verdict: not applicable

Renovate

  • Runs on Gitea. Its one advantage.
  • Version source is the registry. IQ input needs custom rules on each run.
  • Two actors on one PR. Renovate rebases, the agent pushes tests. The commits conflict.
verdict: not for this flow

Sonatype Developer automated PRs v4

  • IQ scans the default branch and opens a golden version bump PR. Right idea, right input.
  • SCM list: GitHub, GitLab, Bitbucket, Azure DevOps. Gitea is not supported.
  • No tests, no baseline. If the code moves to a supported SCM, this becomes the bump step and the agent keeps the tests.
verdict: not applicable on Gitea

Pi agent, started by Jenkins

  • Runs in print or JSON mode. One Jenkins step.
  • Reads the IQ result. Maps the jar. Writes the tests. Runs before and after. Opens the PR on Gitea.
  • One actor owns the branch, the tests, and the PR text.
verdict: selected

Guard rails that Jenkins must add

  • Permit the categories in section 09 only. Check the version before the PR opens.
  • Permit changes to pom files and new test files only.
  • Both test runs must pass. A failed "before" run goes to Dev.
  • Rebase the branch when main moves.

Gate rule on feature branches

If the PR adds a new vulnerable dependency, the gate fails. The developer who added it fixes it before the merge. If the finding already exists on main, the gate does not block the PR. The repair job on main fixes it.

Waivers v3

SecOps can accept a finding with a waiver that has an expiry date. The repair job reads the active waivers before it sorts the findings. A waived finding does not get a fix. The score report shows it as "waived until date". Without this step, the agent fixes findings that SecOps has accepted, and the daily report overstates the open risk.

Write-back after the merge, optional v3

Today the loop ends in Jenkins. The pull request merges. The next scan is clean. IQ forgets the violation. SecOps sees "violation gone" but not "fixed by pull request X on date Y". The write-back adds one API call after the merge. The job posts the pull request link, the merged commit, and the version change as a comment on the violation. The next scan closes the violation. The comment stays in the IQ history. SecOps and the auditor see the evidence in IQ. Nobody opens Jenkins or Gitea. This step is not required for the flow. Keep it as a PoC stretch item.

Scan input matters

IQ reachability analysis works on compiled classes, not on the pom. The Jenkins scan step must point IQ at target/ with the built jar and the classes. If the current scan reads pom.xml only, securityReachable is empty for every finding and our skill is the only reachability source. This is the first check in the PoC.

08Jocata Vulnerability ScoreEvery finding gets a fix. The score orders the queue›

Clients of a financial nature read the report. They do not read the code. A vulnerable jar in the report must be fixed, even if the code does not call it, unless SecOps has an active waiver on it. The reachability check does not remove a finding. It sets the priority and the test depth.

InputSourceWeightRule
SeverityIQ CVSS score40CVSS 9 to 10 = 40. 7 to 8.9 = 30. 4 to 6.9 = 15. Below 4 = 5.
ReachabilityTwo sources: IQ securityReachable per CVE, and the agent map from section 10 per class20Either source says called = 20. Called by config only = 15. Both say not called = 5. Sources disagree = 20 and a review flag.
ExposureService metadata15Internet-facing = 15. Internal = 8. Batch = 3.
Exploit in the wildCISA KEV list, EPSS from IQ15Known exploit = 15. EPSS above 0.5 = 10. Else 0.
Client commitmentContract SLA for the product10Client audit due in 30 days = 10. Else 0.

Where the score sits in the flow

  1. Stage 4 computes the score for each finding after the sort.
  2. The repair job processes findings in score order. P1 first.
  3. The pull request shows the score and the five inputs for each component.
  4. The daily report shows open findings by band. This is the view for the client audit.
  5. The monthly token budget applies to P3 and P4 first. P1 and P2 do not stop for budget.

Two reachability sources v3

  • IQ answers "does the application reach the vulnerable method of this CVE". Yes or no per CVE. Free with the scan, if the scan includes compiled classes.
  • The agent skill answers "which of our classes call this jar". A class list. The test writer needs this list.
  • Keep both. IQ is the score input. The skill is the test input.
  • The two answers should agree. If IQ says reachable and the skill finds no caller, or the reverse, the finding gets the higher score and a review flag in the PR. A disagreement is a signal, not an error.

If the server version does not export EPSS, use CVSS only and give reachability a weight of 30. The PoC confirms this.

09Usage categoriesCalled, called by config, not called. What the PR says›

The usage result from the agent map gives a third dimension to the sort. It decides the test depth, and it permits a major upgrade or a removal when no code calls the jar.

What the pull request says for a jar that is not called

Component: com.fasterxml.jackson.core:jackson-databind 2.15.2 to 2.15.4
CVE: CVE-2024-XXXX, CVSS 7.5
Usage: No class in this repository calls this jar. The jar is a transitive dependency of spring-boot-starter-json 3.1.5.
Evidence: Compile passed. Unit suite passed, 412 tests. Integration suite passed, 38 tests. Application start check passed.
New tests: None. There is no caller to test.
Jocata Vulnerability Score: 45, P3. Reachability input: 5, not called.
Commands run: mvn dependency:tree, jdeps -verbose:class, rg. See usage-result.json.

The reviewer then knows two facts. The fix is a version change only. The absence of new tests is a decision, not an omission.

Limits of "not called"

A static search can miss usage. Before the agent marks a jar as "not called", it runs the indirect checks in section 10: reflection, Spring auto-configuration, SPI loaders, configuration files, annotations. If any check finds the jar, the result is "called by configuration".

10How the agent maps a jar to the codedependency:tree, jdeps, rg, indirect checks›

The agent does not guess. Deterministic commands make the map from the jar to the classes. The LLM reads the map and the code. The map is the evidence in the pull request. A reviewer can run the same commands and get the same result.

Step 1. Find the jar in the dependency tree

mvn dependency:tree -Dincludes=com.fasterxml.jackson.core:jackson-databind

A path of one level is a direct dependency. A longer path is transitive, and it shows the library that brings the jar.

Step 2. Find the classes inside the jar

unzip -l ~/.m2/repository/com/fasterxml/jackson/core/jackson-databind/2.15.2/jackson-databind-2.15.2.jar | grep '\.class$'

The agent reads the class names and makes a package list. Your code must use these names if it calls the jar.

Step 3. Find your classes that use those packages

Method A, source search. Fast. Works before compile.

rg -l "import com\.fasterxml\.jackson\.databind" src/main/java
rg -l "com\.fasterxml\.jackson\.databind\." src/main/java src/main/resources

Method B, bytecode analysis with jdeps. Exact. Shows your class, the jar class it calls, and the jar.

mvn compile -q
jdeps -verbose:class -cp "$(mvn dependency:build-classpath -q -Dmdep.outputFile=/dev/stdout)" target/classes \
  | grep "jackson-databind"

# output
com.jocata.payments.api.PaymentMapper -> com.fasterxml.jackson.databind.ObjectMapper  jackson-databind-2.15.2.jar
com.jocata.payments.api.PaymentMapper -> com.fasterxml.jackson.databind.JsonNode      jackson-databind-2.15.2.jar

Step 4. Find indirect usage

CheckCommand or rule
Reflectionrg "Class\.forName|\.loadClass\(" src/main/java and compare the strings with the package list.
Spring auto-configurationThe jar is on the classpath and a Spring starter is present. Treat as "called by configuration".
SPI loadersunzip -l <jar> | grep META-INF/services. If present, the jar loads at start.
Configuration filesrg "com\.fasterxml\.jackson\.databind" src/main/resources for XML, YAML, properties.
Annotationsrg "@Json" src/main/java for annotation packages inside the jar.

Step 5. Give the map to the LLM

The LLM gets the map, the source of each class in the map, and the changelog between the two versions. Its task is narrow: for each class, write a test that calls the public methods which use the jar, and assert the current result. It does not search the codebase. The commands did the search.

The jar-to-code map is the same procedure on every run. Put the procedure in a skill. The agent loads the skill, runs the scripts, and reads the result. The skills connect through JSON files, not through the LLM memory.

name: maven-jar-usage
description: Map a Maven jar (groupId:artifactId:version) to the classes in this repository that use it. Use before you write tests for an OSS upgrade.
---
## Input
- GAV of the vulnerable jar
- Repository root

- Do not change pom.xml in this skill.

12End-to-end flowGate order, ten stages, 57 steps, with exits›

Each step is one action. Each decision shows its exit. v2, v3, and v4 mark steps that changed in that version.

Gate order in the repair job v4

1

Trigger and build

  1. A merge to main starts the build. Or an IQ webhook on a new violation, or the daily schedule, starts the repair job for a protected branch. v3
  2. Jenkins compiles the code and runs the unit tests.
  3. Jenkins makes the build artifact.
2

Sonatype IQ scan

  1. The Sonatype Jenkins plugin sends the compiled classes and the jar in target/ to IQ Server for a policy evaluation. v3
  2. IQ Server scans each component in the artifact.
  3. IQ Server returns the result. For each finding: the component, the CVE, CVSS, EPSS, securityReachable, InnerSource attribution, the remediation type, and the remediation version. v4
  4. The plugin returns the scanId, the report URL, and the policy result to the build. No parsing. v3
  5. If there is no security policy violation on a Maven component, the build is successful for this flow. Licence violations and other ecosystems go to Dev. v4 exit: green
  6. If there is one or more violations, the build fails. Jenkins keeps the build red.
3

Start the repair job

  1. Jenkins starts the separate job "OSS repair" with the branch, the commit, the scanId, and the report URL from the plugin.
  2. The job calls the Priorities API with includeRemediation=true. v2
  3. The job reads the active waivers for the application. A waived finding leaves the queue and is reported as "waived until date". v3 exit: waived
  4. The job checks for an open pull request for the same branch and the same components, in Gitea or in the IQ violation comment.
  5. If an open pull request exists, the job stops. exit: duplicate
  6. If no open pull request exists, the job continues.
4

Map, sort, and score

  1. For each finding, the job runs the maven-jar-usage skill, per module when the version is a property or sits in a parent pom. Result: called, called by config, or not called. v4
  2. If the dependency tree shows the jar under an InnerSource library, the job routes the finding to the library repository and marks the consumer finding "blocked on upstream". For P1 and P2, a temporary override continues in the consumer. v4 exit: upstream
  3. The job picks the remediation version in the order of section 07: golden version first, then next-no-violations. For a library bump, inner-source-latest-non-breaking. v4
  4. If no version is present, the job sends the finding to Dev. exit: Dev
  5. The job checks that the chosen version is downloadable through Nexus Repository. If not, it logs an error with the GAV and the repository and marks the finding "blocked on artifact". v4 exit: artifact
  6. The job compares the current version and the chosen version: minor or major.
  7. If the jar is called and the upgrade is major, the job sends the finding to Dev. exit: Dev
  8. All other findings stay in the automated path. Each gets a category from section 09. v2
  9. The job computes the Jocata Vulnerability Score. Reachability uses IQ securityReachable and the skill result. A disagreement sets a review flag. v3
  10. The job orders the findings by score across all repositories. P1 first. It applies the per-day cap on new pull requests and the token budget for P3 and P4. v4
5

Pi agent: tests for called jars

  1. The Pi agent makes a branch oss-auto-fix/<scanId> from main, as the bot account. v4
  2. For a jar that is not called, the agent skips to Stage 6. No new tests. version only
  3. For a called jar, the agent reads usage-result.json and checks if tests exist for the listed classes.
  4. If tests exist, the agent uses those tests.
  5. If no tests exist, the agent runs write-characterization-tests. The LLM writes tests for the listed classes. The tests record the current behavior.
  6. The agent runs the tests on the current jar version.
  7. If a test fails on the current version, the agent stops for that finding. It sends the finding and the test to Dev. A failed baseline is not valid evidence. exit: Dev
  8. If all tests pass, the agent saves before-report.xml.
6

Pi agent: upgrade or remove

  1. For a declared jar that is not called, the agent removes the dependency from the pom. v2
  2. For all other jars, the agent sets the chosen version where it is defined: the property, the parent pom in this repository, or the dependency itself. For a transitive jar, it adds the version to dependencyManagement. v4
  3. The agent compiles the code. When a property or a parent pom changed, this is the full reactor build. v4
  4. If the compile fails after a removal, the agent restores the dependency and applies the upgrade instead. v2
  5. The agent runs the full unit suite, the integration suite, the new tests, and the application start check, for every module touched.
  6. The agent saves after-report.xml.
  7. If the compile or a test fails, the agent removes that component from the pull request. It sends the finding, the error, and the reports to Dev. exit: Dev
7

Pull request on main

  1. The agent commits the pom change and the new tests.
  2. The agent pushes the branch to Gitea.
  3. The agent runs gitea-pull-request. One pull request for all fixes from one scan.
  4. For each component, the pull request has: CVE, old and new version, IQ remediation type, IQ report URL, usage result from both sources, callers, modules touched, before and after reports, score with its five inputs, review flag if any, and the commands run. v4
  5. For a jar that is not called, the text states it. For a removal, the text states it. For a temporary InnerSource override, the text names the library release that removes it. v4
  6. The agent marks the new tests as characterization tests and adds the label oss-auto-fix.
8

Verify and merge

  1. The pull request starts the Jenkins PR build.
  2. Jenkins runs the build, the tests, and the IQ scan again.
  3. If the IQ scan is clean and the tests pass, Jenkins marks the pull request green.
  4. A reviewer checks the evidence. The reviewer does not test the fix manually. A "major, not called, transitive" component gets a Dev reviewer. v2
  5. The reviewer merges the pull request. Or, if the policy permits, Jenkins merges it automatically. Branch protection on main stays; the bot cannot push to main. v4
9

Backport

  1. Jenkins cherry-picks the merged commit to each active release branch and opens a pull request there. v2
  2. Each backport pull request runs its own PR build, tests, and IQ scan. If a release branch has a different jar version, the agent repeats Stages 5 and 6 on that branch.
10

Close

  1. The merge starts a new build. The IQ scan passes. exit: green
  2. Optional: the job posts the pull request link, the commit, and the version change as a comment on the violation in IQ. v3
  3. Jenkins closes the repair job. It records the components, the CVEs, the scores, and the pull request links.
  4. The open findings by band are visible in IQ. The Jenkins report is a copy for the slide. Findings in "blocked on upstream" or "blocked on artifact" return to the queue on the next scan. v4
13ExitsThe eight cases that leave the automated path›

No clean version

Step 19. IQ gives no remediation version. No higher version clears the policy.

Major upgrade of a called jar

Step 22. The code calls the jar and the fix is a major version. API changes need a developer.

Baseline fails

Step 32. A new test fails on the current jar. The test or the code has a problem. The upgrade is not the cause.

Upgrade fails

Step 40. The compile, a test, or the start check fails after the upgrade. The pull request does not include that component.

Token budget or day cap reached

Step 25. The monthly LLM budget or the per-day PR cap is used. P3 and P4 findings go to Dev until the next month. P1 and P2 continue.

Active waiver v3

Step 12. SecOps has accepted the finding until a date. No fix. The report shows "waived until date". The finding returns to the queue when the waiver expires.

Blocked on upstream v4

Step 17. The jar sits inside an InnerSource library. The library is fixed first. The consumer waits for the release, or carries a temporary override for P1 and P2.

Blocked on artifact v4

Step 20. The chosen version is not downloadable through Nexus Repository. Error logged with the GAV. The repository admin unblocks it.

What the tests prove

The tests show that the upgraded jar does not break your code. The tests also increase the code coverage, because the code has no tests today. The tests do not prove that the vulnerability is gone. The IQ report is the evidence for that.
