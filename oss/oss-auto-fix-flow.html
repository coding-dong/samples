Product Review Framework · Business Case

Automated repair of minor OSS vulnerabilities

From a code commit to a merged fix. Nexus IQ finds the vulnerability. Jenkins controls the flow. A Pi agent writes the tests and the fix. A person only reviews the evidence.

Why the flow does not use Dependabot or Renovate

Dependabot and Renovate are good tools for one task. They change a version number and open a pull request. This flow needs four more tasks. The bots cannot do those tasks. The table shows the comparison.

Dependabot

  • Its security updates come from the GitHub advisory database. This flow does not use that database.
  • It does not read a Nexus report.
  • It does not write tests. It does not run a baseline.
  • It works on GitHub. The code is on Gitea.
verdict: not applicable

Renovate

  • It runs on Gitea. This is its one advantage over Dependabot.
  • Its version source is the package registry. Nexus input needs custom rules on each run.
  • It does not write tests. It does not run the "before" report.
  • Two actors on one pull request. Renovate rebases the branch. The agent pushes tests. The commits conflict.
verdict: not for this flow

Pi agent, started by Jenkins

  • Runs in print or JSON mode. Jenkins calls it as one step.
  • Reads the Nexus report. Changes the pom. Finds the callers. Writes the tests. Runs the tests before and after the upgrade.
  • Opens the pull request on Gitea with the tests and both reports.
  • One actor owns the branch, the tests, and the pull request text.
verdict: selected

Guard rails that Jenkins must add

The agent does not get the limits that the bots give for free. Jenkins must apply them.

  • Permit minor upgrades only. Check the version before the pull request opens.
  • Permit changes to the pom files and to new test files only.
  • Both test runs must pass. A failed "before" run goes to Dev.
  • Rebase the branch when the release branch moves.

End-to-end flow: from commit to merged fix

Each step is one action. Each decision shows its exit.

1

Commit and build

  1. A developer pushes a commit to a release branch on Gitea.
  2. Gitea sends a webhook to Jenkins.
  3. Jenkins starts the build job for that branch.
  4. Jenkins compiles the code and runs the unit tests.
  5. Jenkins makes the build artifact.
2

Nexus scan

  1. Jenkins sends the artifact to Nexus IQ for a policy evaluation.
  2. Nexus IQ scans each component in the artifact.
  3. Nexus IQ returns a report. For each finding, the report has the component, the CVE, the severity, and the recommended version.
  4. Jenkins reads the policy result.
  5. If the report has no policy violation, the build is successful. The flow stops here. exit: green
  6. If the report has one or more policy violations, the build fails. Jenkins keeps the build red.
3

Start the repair job

  1. Jenkins starts a separate job, "OSS repair", for the failed build. The job gets the branch name, the commit, and the Nexus report.
  2. The job checks Gitea for an open pull request for the same branch and the same components.
  3. If an open pull request exists, the job stops. This prevents duplicate pull requests. exit: duplicate
  4. If no open pull request exists, the job continues.
4

Sort the findings

  1. The job reads each finding in the Nexus report.
  2. The job compares the current version and the recommended version.
  3. If the recommended version is a major upgrade, the job sends the finding to Dev. Dev uses the current manual flow. exit: Dev
  4. If Nexus does not give a clean version, the job sends the finding to Dev. exit: Dev
  5. If the recommended version is a minor upgrade, the job gives the finding to the Pi agent.
5

Pi agent: analyze

  1. The Pi agent makes a new branch from the release branch.
  2. The Pi agent finds the component in the pom files. It records if the component is direct or transitive.
  3. The Pi agent searches the source code for classes that call the component.
  4. If no class calls the component, the Pi agent marks the finding as "transitive, not called". It goes to Stage 7 for this finding. skip tests
  5. If one or more classes call the component, the Pi agent lists those classes.
6

Pi agent: write and check the tests

  1. The Pi agent checks if JUnit tests or integration tests exist for the listed classes.
  2. If tests exist, the Pi agent uses those tests.
  3. If no tests exist, the Pi agent writes characterization tests for the listed classes. The tests record the current behavior.
  4. The Pi agent runs the tests on the current jar version.
  5. If a test fails on the current version, the Pi agent stops for that finding. It sends the finding and the test to Dev. A failed baseline is not valid evidence. exit: Dev
  6. If all tests pass, the Pi agent saves the test report as "before".
7

Pi agent: upgrade

  1. The Pi agent changes the version in the pom to the Nexus recommended version. For a transitive component, it adds the version to dependencyManagement.
  2. The Pi agent compiles the code.
  3. The Pi agent runs the full unit test suite, the integration tests, and the new tests.
  4. The Pi agent saves the test report as "after".
  5. If the compile or a test fails, the Pi agent removes that component from the pull request. It sends the finding, the error, and the reports to Dev. exit: Dev
8

Pull request

  1. The Pi agent commits the pom change and the new tests to the branch.
  2. The Pi agent pushes the branch to Gitea.
  3. The Pi agent opens one pull request on Gitea for the release branch. The pull request has all minor fixes from one Nexus report.
  4. The pull request description has, for each component: the CVE, the old version, the new version, the Nexus reference, the list of classes that call the component, and the "before" and "after" test reports.
  5. The Pi agent marks the new tests as characterization tests.
  6. The Pi agent adds the label oss-auto-fix to the pull request.
9

Verify and merge

  1. The pull request starts the Jenkins build job for that branch.
  2. Jenkins runs the build, the tests, and the Nexus scan again.
  3. If the Nexus scan is clean and the tests pass, Jenkins marks the pull request as green.
  4. A reviewer checks the pull request. The reviewer does not test the fix manually. The reviewer confirms that the reports are present and green.
  5. The reviewer merges the pull request. Or, if the policy permits, Jenkins merges the pull request automatically.
10

Close

  1. The merge starts a new build on the release branch.
  2. The Nexus scan passes. The build is successful. exit: green
  3. Jenkins closes the repair job. It records the components, the CVEs, and the pull request link.
  4. For each other active release branch, the next build repeats this flow from Stage 1. Each branch gets its own pull request.

Exits to Dev

Major upgrade

Step 18. The recommended version is a major version. The current manual flow applies.

No clean version

Step 19. Nexus does not give a version with zero vulnerabilities.

Baseline fails

Step 30. A new test fails on the current jar. The test or the code has a problem. The upgrade is not the cause.

Upgrade fails

Step 36. The compile or a test fails after the upgrade. The pull request does not include that component.

What the tests prove

The tests show that the upgraded jar does not break your code. The tests also increase the code coverage, because the code has no tests today. The tests do not prove that the vulnerability is gone. The Nexus report is the evidence for that.
